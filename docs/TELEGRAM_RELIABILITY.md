# Приоритет: устойчивый приём сообщений Telegram

Задача: бот должен начинать опрос без ожидания необязательной настройки меню,
восстанавливаться после сетевых сбоев и предоставлять проверяемое состояние
получения обновлений. Рабочий `getMe` и активный процесс сами по себе не
подтверждают приём сообщений.

## Критерии приёмки

- Перед опросом проверяется личность бота и отключается webhook без удаления
  ожидающих обновлений. Настройка меню и команд выполняется параллельно опросу.
- Работает один штатный poller. Существующее управление offset и повторами
  aiogram сохраняется. Внешние проверки не вызывают второй `getUpdates`.
- Каждый успешный ответ `getUpdates`, в том числе пустой, обновляет счётчик
  и время приёма. Ошибки опроса, отправки и обработчиков учитываются раздельно.
- Состояние относится к текущим PID и systemd InvocationID. Старый файл от
  предыдущего запуска не считается подтверждением работоспособности.
- Отсутствие heartbeat более 45 секунд или успешного опроса более 180 секунд
  отмечается монитором. Отсутствие пользовательских сообщений не считается
  сбоем: пустые ответы Telegram допустимы.
- Завершённая обработка реального входящего обновления с успешным ответом
  `sendMessage` отмечает `last_roundtrip_at`. Без такого события сквозная
  проверка остаётся неподтверждённой, даже при успешном опросе очереди.
- Не записываются тексты, контакты, chat/user/update ID, токены и URL запросов.
  Файл состояния приватный; на VPS: `/var/lib/bratstvo-bot/health.json`.
- После транспортной ошибки очищается DNS-кэш прямого соединения; активные
  запросы не закрываются. Middleware не повторяет отправку сообщений.
  TLS и проверка сертификата сохранены; новые прокси не подключаются.

## Оповещения

Обычные напоминания о днях рождения, сроках и мероприятиях помечаются
отправленными только после успешного ответа Telegram. Для просроченной задачи
и мероприятия подтверждения ведутся отдельно по получателям: сбой одной
доставки не вызывает повтор уже подтверждённых при следующем цикле.
Миграция добавляет две логические колонки в `tasks` и дату в `event_attendance`;
старые общие флаги сохраняются, прежние уведомления массово не переотправляются.
При падении процесса между внешней отправкой и фиксацией в БД повтор всё же
возможен: транзакция БД не может атомарно охватить Telegram Bot API.

`OPERATIONS_ALERT_TELEGRAM_ID` — явно выбранный владельцем числовой ID личного
или служебного чата. Пустое значение отключает отправку. Получатель никогда
не выбирается автоматически по роли или списку superuser.

О сбое сообщается после двух последовательных неуспешных проверок. Повтор
одного состояния — не чаще раза в 30 минут. О восстановлении сообщается
отдельно. Если Telegram недоступен во время сбоя, инцидент остаётся в
приватном `alert-state.json`, и после восстановления приходит сообщение.
При неизвестном результате отправки мгновенного повтора нет; абсолютную
однократность внешней доставки Bot API не гарантирует.

Контроль остаётся на существующем VPS: полный отказ сервера или Telegram
может остановить и доставку оповещения. Независимый внешний монитор и
резервный канал уведомлений этим изменением не создаются.

## Проверка

После установки проверить свежесть `health.json`, рост `poll_successes`,
соответствие PID/InvocationID и отсутствие ошибок `bratstvo-monitor.service`.
Для подтверждения входящего сообщения и ответа владелец отправляет `/start`
в личном чате с ботом. Только после успешного ответа должна появиться свежая
метка `last_roundtrip_at`. Генерировать входящие обновления от имени людей
или сбрасывать очередь для теста нельзя.

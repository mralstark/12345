# Обновление уже работающего сервера

На Windows из Git-копии проекта:

```powershell
.\.venv\Scripts\python.exe deploy\update_vps.py root@31.129.98.217
```

Можно использовать Python из соседнего локального проекта:

```powershell
& E:\self\12345-main\.venv\Scripts\python.exe E:\self\12345-repo\deploy\update_vps.py root@31.129.98.217
```

Перед этим проверить тесты и закоммитить файлы: Git-версия отправляет только
отслеживаемые файлы. Обновление сохраняет серверный `.env`, PostgreSQL и загрузки.
SSH-ключ выбирает обычная настройка OpenSSH. Приватные ключи не входят в архив.

Порядок: проверка контрольной суммы, зашифрованный бэкап данных, копия прежнего кода
в закрытом `/opt/bratstvo-releases`, установка зависимостей с проверкой хешей,
короткая остановка сервисов, аддитивные миграции, запуск и проверка ответа API.
Параллельное обновление блокирует `flock`. Конфигурация nginx и сертификат сохраняются.

При ошибке после остановки скрипт возвращает прежний код и запускает сервисы.
Миграции не откатываются автоматически: новые таблицы/колонки совместимы с прежним
кодом, а данные и архивные награды сохраняются. Перед повторной попыткой проверить
причину в журналах. Восстановление базы из резервной копии — отдельная операция:
не применять его поверх работающего сервиса без оценки изменений после бэкапа.

Схема: сначала `migrate_operational_roles_and_reviews`, затем
`migrate_cabinet_revisions`, затем `migrate_gamification`. Повторное применение безопасно.
SQLite используется для локальной проверки; серверная PostgreSQL остаётся источником данных.

Проверить после обновления:

```bash
systemctl is-active bratstvo-api bratstvo-bot nginx postgresql
curl --fail https://lk.31-129-98-217.sslip.io/healthz
journalctl -u bratstvo-api -u bratstvo-bot --since '5 minutes ago' --no-pager
```

В Telegram закрыть и вновь открыть Mini App. Имеющийся механизм версий `app.js`
и `styles.css` обновляет адреса ресурсов автоматически.
